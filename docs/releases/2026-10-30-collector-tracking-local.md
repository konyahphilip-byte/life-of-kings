## Implemented code

An assigned Waste provider with an active account, provider role, approved current profile and an approved Waste review for that exact profile revision can start a 30-minute sharing lease. Every API read/write rechecks the current job, participants, account state, approval revision and either-side request blocks under the existing user/job transaction locks. Only that job's customer and assigned collector can read. A pending role or a generic approval is insufficient. Collector reassignment, review revocation, blocks and terminal job states deny future publication or exposure. Existing job finish/complete/cancel/dispute transitions clear the latest coordinate in the same transaction.

The collector first chooses separate customer-sharing consent. Only after server admission does an explicit Start action call the browser's official `watchPosition` permission flow. No on-load prompt, location request on the customer device, library/contacts access, background collection, AI processing or coordinates in browser storage/logs/audit is added. Unsupported status queries never imply permission. Denial is latched; revocation or resetting access to Ask stops capture. Hidden/offline/page exit/unmount/account change, expiry and replacement sessions stop the native watch. The optional browser permission controls in draft30 are not silently copied or deployed by this independent increment.

Standard/Saver/Extreme publish at most once per6/12/25seconds and customer pages refresh about5/10/15seconds after completion. Only one position write is in flight, with one latest in-memory pending sample. Offline/error stops collection instead of queuing a location history. Server confirmation is required before reporting a shared position; loss of Stop confirmation is stated honestly. There is no background push or websocket subscription claim.

The server stores only the latest coordinate with device-reported accuracy and timestamps. It validates numeric bounds, maximum1000m accuracy, freshness, strictly increasing sequence/time and minimum3seconds between new positions. Exact retries cannot rewrite a coordinate or revive a paused/old sharing request. Stable start operation IDs, captured owner IDs, CSRF/origin checks, API rate limits and transaction rollback protect retries and account changes. Device location is an estimate, not proof of presence, arrival, measured waste or completed work.

At30seconds the position is labelled stale; at90seconds the UI hides it. The server clears old coordinates on access or its30second maintenance cycle, so physical live-table cleanup can take up to approximately120seconds during normal operation. No permanent position history is stored. Existing database backups have their own retention; this is not a promise of backup erasure. Sharing expires at30minutes. Cleanup errors log only a fixed event name/time. `ECOVIBES_TRACKING_DISABLED=true` is a deny-only operational switch. Missing PostgreSQL migration marker returns503 for tracking while existing workflows remain available.

## Interfaces and exact scope

`GET /api/v1/jobs/:jobId/tracking` returns the authenticated owner, role, current state, current lease, sequence, server/check timestamps, accuracy and latest allowed point. POST subroutes are `start`, `point`, `pause` and `stop`. Each write carries `expectedOwnerId`; point/stop are tied to the captured sharing session. Start additionally requires `shareWithCustomer:true`, a fresh request time and a stable UUID. No user/collector selectors are accepted in the query.

Source: new `server/job-tracking.mjs` and its tests; `server/index.mjs` integration; HTTP/PostgreSQL scripts; additive migration20261029210000; `LocationTracking.tsx`/`location-publisher.ts` and tests; `WasteHub.tsx` account-scoped integration; Waste CSS; self-only document geolocation policy; privacy notice; existing release CI extension. No additional package dependency. Location controls are lazy loaded, approximately12.2kB/4.6kB gzip in the local build.
